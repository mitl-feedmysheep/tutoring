## 2단계: DB 설계

### 한 일
- 요구사항을 테이블로 옮긴 설계 문서 `docs/db-design.md` 작성 (13개 테이블, 격리 규칙, 관계 요약)
- 요구사항 추가: 공부 기록 하루 여러 건(STUDY-01), 게시판 제목+댓글(BOARD-04), 학생 비활성화(ADMIN-04)

### 결정한 것
- **복합 외래키로 격리**: 부모에 `UNIQUE (teacher_id, id)`, 자식은 `(teacher_id, xxx_id)`로 참조. 앱 코드에 버그가 있어도 다른 선생님 데이터와 연결되는 행은 DB가 거부함
- **PK는 UUID v7**: 순번 노출 방지, 시간순 정렬로 인덱스 효율
- **선생님·학생 테이블 분리**, 로그인 화면은 하나. 학생 이메일은 전체에서 유일 (로그인 때 선생님 선택 불필요)
- **`session_version`**: 비밀번호 변경·초기화 때 올려서 기존 로그인을 끊음
- **예약 취소는 `canceled_at`으로 남김**: 고정 일정 자동 예약이 일부러 취소한 회차를 다시 잡지 않도록
- **고정 일정은 KST 요일·분으로 저장**: 벽시계 규칙이라서 (UTC 저장 원칙의 예외)
- **선생님 본인 공부 기록은 별도 테이블**: 학생 조회에 섞일 일이 없고, Prisma가 일부만 NULL인 복합 관계를 지원하지 않음
- **수업 노트는 한 테이블 + author 구분**: 학생 조회는 항상 `author = STUDENT` 조건을 공통 함수에 넣고 테스트
- 공부 기록은 하루 여러 건, 학생은 삭제 대신 비활성화, 게시판은 제목+본문+댓글 (사용자 결정)
- 알림(5단계), Google Meet(6단계) 컬럼은 그 단계에서 추가

## DB 설계 1차 검수 (사용자)

### 바뀐 것
- `invite` 테이블 삭제: 초대 링크를 서명된 토큰(teacherId, inviteId, 1시간 만료)으로. 1회용은 `student.invite_id` UNIQUE로 막음. 발급 링크 목록·중간 취소는 포기
- `teacher_study_log` 삭제: `study_log.student_id`가 NULL이면 선생님 본인 기록
- `study_photo` + `material` → `file` 하나로 통합. 올린 사람(`uploader_student_id`)과 `kind`로 구분
- `board_post`, `board_comment` → `board`, `comment`
- 선생님 고정 수업 시간 `weekly_slot` 추가 (요구사항 SCH-11, SCH-12 추가). 학생 고정 일정은 `weekly_booking`으로 바꾸고 선생님 고정 시간 중에서 고르게 함 (SCH-04 수정)
- 테이블 13개 → 11개

### 결정한 것과 이유
- 앞서 "Prisma가 일부 컬럼만 NULL인 복합 관계를 지원하지 않는다"고 적었던 건 틀렸음. Prisma 6.19로 직접 검증해보니 지원됨. MySQL도 복합 외래키 중 NULL이 있으면 검사를 건너뛰므로 study_log 통합에 문제없음
- `file`은 인투디헤븐 media의 `entity_type` + `entity_id` 방식을 따르지 않음. 외래키를 걸 수 없어서 격리 규칙이 빠지기 때문. 첨부 대상은 `study_log_id` 같은 실제 컬럼으로 둠
- 자식 테이블의 `teacher_id` 중복은 정규형 위반이지만 격리를 위해 유지. 복합 외래키로 불일치는 생기지 않음
- 고정 시간 슬롯 자동 생성: 등록 때 2주치, 이후 매일 새로 범위에 들어온 날짜만 생성 → 선생님이 지운 주는 다시 생기지 않음

- 초대 가입은 `used_at` 조건부 UPDATE가 1행일 때만 학생 생성 → 동시 가입 방지

## DB 설계 3차 검수 (사용자)

### 바뀐 것
- 예약 가능 기간: 1~2주 제한 없앰. 만들어진 앞으로의 슬롯이면 언제든 예약·취소·변경 (SCH-06 → SCH-13). 지난 수업 변경 불가, 30분 전 규칙 유지
- 학생 고정 일정 변경 때 "이번만 / 앞으로 전부" 선택 (SCH-14)
- 선생님 고정 시간 변경·삭제: 학생 없으면 즉시, 있으면 다음 달부터. 시간 변경이면 학생 고정 일정이 따라감, 삭제면 이번 달 말에 끝 (SCH-15)
- 선생님이 학생 수업·고정 일정을 직접 바꿀 수 있음 (SCH-16) → `lesson.canceled_by` 추가
- `weekly_slot`, `weekly_lesson`에 `active_from`, `active_until` 추가. 바꿀 때 행을 고치지 않고 기간을 끊고 새 행을 만듦
- 고정 수업 누락 알림 (NOTI-06)
- 검수 페이지 관계도가 안 보이던 문제 수정: 문법은 정상, 페이지가 mermaid를 자동으로 그리지 않아서 라이브러리를 직접 불러 그리게 함

### 결정한 것과 이유
- 고정 스케줄은 유지. 매주 직접 예약하게 하면 잊는 학생이 생기고 선생님이 일정을 미리 알 수 없음
- 선생님 고정 시간 변경·삭제 때 푸시 알림은 보내지 않음 (사용자 결정). 학생 일정 화면에 안내만 표시
- 대신 월말 다음 달 수업 생성 때, 고정 수업이 하나도 안 만들어진 학생에게만 알림. 그 시점엔 다음 달 슬롯이 이미 열려 있어서 바로 새로 고를 수 있음
- 적용 기간 방식: 고정 일정 이력이 남고, "다음 달부터" 같은 예약 변경을 별도 대기 테이블 없이 표현 가능. 대신 같은 시간 기간 겹침은 UNIQUE로 못 막아서 앱에서 검사

## DB 설계 4차 검수 (사용자)

### 바뀐 것
- 선생님이 학생 수업·고정 일정을 바꾸면 학생에게 알림 (NOTI-07). 선생님 고정 시간 변경은 알림 없음
- 고정 수업 누락 알림(NOTI-06)은 고정 일정 중 하나라도 빠지면 보냄 (화·목 중 목만 없어져도)
- `weekly_slot`, `weekly_lesson`의 `active_from`, `active_until` 제거 → `deleted_at` 하나로

### 결정한 것과 이유
- 적용 기간 칸이 필요 없었음: 이번 달 수업은 이미 만들어져 있으므로, 고정 시간·고정 일정 행을 바로 고치면 다음 생성부터 자연스럽게 반영됨. "다음 달부터 적용"이 별도 칸 없이 성립
- 삭제만 `deleted_at`으로 남김: 학생이 있던 고정 시간을 지울 때, 월말 생성에서 누구에게 알림을 보낼지 알아야 하고 학생 화면에 "다음 달부터 없어져요"를 보여줘야 해서
- 잃은 것: 고정 일정 변경 이력. 요구사항에 없어서 포기
- 월말 생성 당일 생성 후에 고치면 다음 달은 이미 만들어져 있어 그 다음 달부터 반영됨 → 화면 안내로 처리

### 바뀐 것
- 고정 일정 변경 이력 테이블 `weekly_lesson_change` 추가 (SCH-17). 언제, 누가(학생/선생님/시스템), 무엇에서 무엇으로, 사유
- 선생님이 학생 수업·고정 일정을 바꿀 때 사유 필수 (SCH-16), 학생 알림에 사유 포함. `lesson.cancel_reason` 추가
- 테이블 14개 → 15개

### 결정한 것과 이유
- 이력에 요일·시간을 값으로 복사: weekly_slot 시간은 그 자리에서 고치므로 ID만 남기면 원래 시간을 알 수 없음
- 선생님이 고정 시간을 바꾸면 해당 학생마다 이력을 남김 (사유 필수)
- 사용자 질문 정리: slot은 선생님 쪽 수업 시간(학생 0명이어도 존재, 1:다 공유, Meet 링크), lesson은 학생별 참여(출석·노트·취소가 학생마다 다름). 수업 취소는 lesson을 지우지 않고 canceled_at 표시 (수업 이력, 사유 보존)

### 남은 일
- 스키마 생성, Prisma 마이그레이션

## DB 설계 6차 검수 (사용자)

### 바뀐 것
- `weekly_lesson_change` → `schedule_change`로 통합. 수업 1회 취소·옮기기(lesson_id)와 고정 일정 변경(weekly_lesson_id)을 한 테이블에. `lesson.canceled_by`, `cancel_reason`은 이력으로 옮기고 lesson엔 `canceled_at`만
- 모든 테이블 소프트 삭제 (`deleted_at`), 공통 컬럼 `id`, `created_at`, `updated_at`, `deleted_at` (NFR-08)

### 결정한 것과 이유
- 고정 일정 변경을 lesson마다 남기지 않음: "앞으로 전부" 한 번에 수업 여러 개가 바뀌어 같은 사유가 반복되고, 아직 안 만들어진 다음 달 수업엔 붙일 곳이 없음. 그래서 weekly_lesson에 한 줄, 수업 1회 변경은 lesson에 한 줄
- 이력의 전·후는 글자(`before_text`, `after_text`)로 남김. 보여주기만 하면 되고, weekly_slot 시간은 그 자리에서 고치므로 ID로는 원래 시간을 모름
- 스키마별 시간대: MySQL에 없음 (global, session만). 임시 DB로 확인: session 시간대를 바꿔도 DATETIME은 그대로, TIMESTAMP만 바뀜. Prisma는 항상 UTC → UTC 저장 유지, DB 도구에선 CONVERT_TZ로 조회
- 소프트 삭제 필터(`deleted_at IS NULL`)는 teacher_id 범위와 같은 공통 계층에서 자동 적용
- 소프트 삭제 때문에 UNIQUE가 지운 행과 충돌 → 다시 만들 땐 되살림. 학생 이메일 재사용 처리는 구현 때 결정
- 취소·비활성·링크 취소는 deleted_at과 별개 상태로 유지 (이력에 보여야 해서)

### 남은 일
- 스키마 생성, Prisma 마이그레이션
- 학생 이메일 소프트 삭제 후 재가입 처리 방식

## DB 설계 7차 검수 (사용자)

### 바뀐 것
- 학생 비활성화·삭제 때 이메일 뒤에 `_deleted_{밀리초 타임스탬프}`를 붙여 비움 (사용자 제안). 같은 이메일로 새 초대를 받아 가입하면 새 계정 (ADMIN-04 수정)
- `student.email` VARCHAR(100) → VARCHAR(150) (표시 붙일 자리). 가입 입력은 100자 제한

### 결정한 것과 이유
- 다시 활성화하면 표시를 떼서 원래 이메일로 복구. 그 사이 같은 이메일로 새 계정이 생겼으면 다시 활성화를 막음 (UNIQUE 충돌 방지)
- 별도 "원래 이메일" 컬럼은 두지 않음. 표시 앞부분이 원래 이메일이라 떼면 됨
- 검수 완료. 다음은 스키마 생성과 Prisma 마이그레이션

## 스키마 생성과 첫 마이그레이션

### 한 일
- `local-mysql`(3306)에 `tutoring`, `tutoring_shadow` 스키마 생성 (utf8mb4_0900_ai_ci, into-the-heaven과 동일)
- 전용 계정 `tutoring`@`%` 생성, 두 스키마에만 권한. 비밀번호는 로컬 `.env`에만 저장
- Prisma 7.10.1 설치 (`@prisma/client`, `@prisma/adapter-mariadb`, `prisma`, `dotenv`), `prisma/schema.prisma`와 `prisma.config.ts` 작성
- 첫 마이그레이션 `20261111085524_init` 적용: 15개 테이블. `schedule_change` CHECK 제약은 SQL에 직접 추가
- DB 격리 확인 (트랜잭션 후 롤백): 선생님 A 소유로 B의 학생 납부 기록 → 외래키 오류로 거부, B 소유 → 성공, 변경 이력 대상 없음 → CHECK 오류, 선생님 본인 공부 기록(student_id NULL) → 성공
- 빌드에 `prisma generate` 추가 (`npm run build`, GitHub Actions), 생성 코드는 git·ESLint 제외
- 로컬 lint, test, Docker 이미지 빌드 통과. 앱 컨테이너에서 `host.docker.internal:3306` 접속 가능 확인

### 결정한 것과 이유
- Prisma 7.10.1: npm `latest` 태그가 8.0 RC를 가리키고 있어서 안정 버전으로 고정
- 외래키는 모두 RESTRICT: 소프트 삭제라 DB 연쇄 삭제를 쓰지 않음. Prisma 기본값(SET NULL)은 복합 외래키에서 teacher_id까지 비우려 하므로 명시적으로 지정
- 선생님 소유 직접 관계(teacher FK)는 부모가 teacher인 테이블에만 둠. 나머지는 복합 외래키가 이미 선생님을 보장
- `prisma.config.ts`에서 `env()` 대신 `process.env`: Docker 빌드 때 DB 정보 없이도 `prisma generate`가 되게
- 마이그레이션 자동 적용(배포 단계)은 아직 넣지 않음. 개발 환경이 없어서 이 Mac mini에서 직접 적용

### 문제와 해결
- 계정 생성 직후 `.env`가 안 만들어짐: 명령 출력 필터(`grep -v`)가 출력이 없을 때 실패로 끝나 뒤 명령이 건너뛰어짐. 계정 비밀번호를 새로 정하고 `.env` 다시 작성
- npm 11이 설치 스크립트를 기본 차단해서 `@prisma/engines` postinstall이 경고로 건너뛰어졌지만, 엔진은 정상 동작 확인

## 배포 실패와 수정
- DB 스키마 커밋(f2e805e) 배포가 "Start container" 단계에서 실패: `Unable to retrieve value from system keyring`. 기존 컨테이너는 그대로 떠 있어서 서비스 영향 없음
- 원인: Mac mini에서 `doppler login`을 하면 로그인 정보가 키체인에 저장되는데, 같은 사용자 계정으로 도는 러너의 Doppler CLI가 그걸 읽으려다 실패 (DOPPLER_TOKEN이 있어도)
- 조치 1: Doppler CLI 로그아웃. DATABASE_URL 등록은 끝났고, 인투디헤븐 백엔드·어드민 배포도 같은 러너에서 Doppler CLI를 써서 그대로 두면 같이 실패함
- 조치 2: 과외 앱 배포 워크플로는 빈 설정 폴더(`--config-dir`)를 써서 앞으로 누가 로그인해도 DOPPLER_TOKEN만 쓰게 함
- 주의: 이 Mac에서 다시 `doppler login`하면 인투디헤븐 배포가 깨질 수 있음. 쓰고 나면 `doppler logout`
